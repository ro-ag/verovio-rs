# Contributing to verovio-rs

Thanks for your interest. This document covers scope, what's accepted,
and the development workflow.

## Scope (what this binding is and isn't)

`verovio-rs` is a **read + play** binding to Verovio. It exposes
everything needed to:

- Load MEI / MusicXML / Humdrum / ABC / PAE
- Render SVG / PNG / single- and multi-page PDF
- Produce SMF MIDI with full multi-track playback control
- Synthesize offline WAV via SoundFont
- Query the timemap, tempo, measures, bbox, score metadata

**Out of scope for 0.x:**

- **MEI editing.** Verovio's `Toolkit::Edit(json)` mutation surface
  is intentionally not exposed. Editing changes the in-memory
  document, which invalidates the cached input that `metadata()`
  relies on, and reopens the safety contract for mutating operations.
  A v1.x track may add editing once the read+play surface has
  stabilized.

- **Humdrum methods (`GetHumdrum*`).** Verovio's
  `Toolkit::m_humdrumBuffer` is a `static char*` shared across all
  instances. Exposing these would break the `Toolkit: Send` guarantee.

- **`SetLocale`.** Mutates `std::locale::global` process-wide; no
  per-instance alternative exists upstream.

- **`GetLog` / `GetLogString` without a mutex story.** The log surface
  has its own crate-level mutex (`set_log_level`); exposing the read
  side would need an equivalent design.

- **Windows support.** Permanently. Don't open issues or PRs adding
  `cfg(windows)`, MSVC detection, or `cmake -G "Visual Studio"`.

- **Live audio device output as a library feature.** The shipped
  `examples/live_playback.rs` demonstrates the cpal + rustysynth
  pattern; productionizing it (transport, seek, multi-stream mixing)
  belongs in the consuming application.

If you want one of the out-of-scope items, the discussion has to start
with how the safety contract changes (see `src/toolkit.rs` docs and
the wiki Concurrency page).

## Build + test workflow

```sh
git clone --recurse-submodules https://github.com/ro-ag/verovio-rs
cd verovio-rs
cargo test                                  # default features
cargo test --features verovio/png,verovio/pdf,verovio/audio
```

NixOS users:

```sh
nix-shell
cargo test
```

Live-playback example (Linux needs `alsa-lib` + `pkg-config`):

```sh
cargo run --release --features live-audio \
    --example live_playback -- path/to/font.sf2
```

## Code style

- **No `unsafe` in the public API of the `verovio` crate.** All
  `unsafe` is generated by `cxx` inside the bridge module.
- **No `panic!` across the FFI boundary.** C++ exceptions are caught
  by `cxx` and surfaced as `Result<_, Error>`.
- **No new `Error` variants without a matching `From` impl** and a
  `Display` arm.
- Match existing naming conventions: `_into` for buffer-reuse,
  `_writer` for `io::Write` streaming-shape, `with_*` for builders,
  typed wrappers for option groups (`MidiOptions`, `SvgOptions`).
- New public items must have rustdoc. Intra-doc links should resolve
  (`cargo doc --no-deps` should produce zero warnings).

## Sanitizers

Run before submitting changes that touch FFI or threading:

```sh
RUSTFLAGS="-C linker=clang -C link-arg=-fuse-ld=lld" \
ASAN_OPTIONS="halt_on_error=1:abort_on_error=1:detect_leaks=0" \
    cargo test --features verovio/sanitize
```

```sh
RUSTFLAGS="-C linker=clang -C link-arg=-fuse-ld=lld" \
    cargo test --features verovio/sanitize-thread --test concurrency
```

The TSan pass currently reports 8 upstream-Verovio races (see the
Concurrency wiki page) — those are acknowledged and not a blocker.
New races introduced by your change are.

## Commits + PRs

- One logical change per commit; prefer focused commits over a big
  blob. The first line is a 50-72 char summary; the body explains the
  why.
- Don't add `Co-Authored-By` trailers from automated tooling.
- PRs against `main`. Include a one-line description of the user-facing
  change in the PR body. Reference any related issue.
- Update `CHANGELOG.md` under `[Unreleased]` for user-visible changes.
- Tests are required for new behavior. The bar is "the test would
  fail before your change."
